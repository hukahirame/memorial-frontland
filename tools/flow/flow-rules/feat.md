# feat — 振る舞いが増える・変わる変更

## 手順

1. 対象システムの `docs/systems/<id>.md` を読む(なければ新規作成)
2. 仕様書の変更案を文面ごと計画に入れる
3. **計画の承認を待つ**(ここで止まる)
4. 仕様書を計画の文面どおりに書き、実装する。文面を変えることになったら承認を取り直す
5. コミットする

## 仕様書の形式

`docs/systems/INDEX.md` の「書き方」に従う。仕様書は受け入れ条件で、欄は 用語・受け入れ条件・やらないこと・未決。

**未決** — 指示から決まらないことを推測で埋めず、ここに落とす。
「任意」(AIが決めてよい)と「未決」(人間が決める)を区別すること。
未決の項目は仮実装で止め、人間の判断を待つ。未決が多すぎるなら指示が粗すぎる合図。

## 解釈の根拠を併記する

計画を提示するとき、仕様書の各欄について「元の指示のどこから、どう解釈したか」を
**チャット上で**報告する(仕様書本文にも計画にも書かない)。

人間はこれを読んで、自分の意図と突き合わせる。仕様書を読み合わせるだけだと、
AIの誤読がそのまま通る。

## テスト

書くのは以下のみ。それ以外は書かない。

- セーブデータの互換性
- サーバー権威ロジック(クライアント入力の検証、重複・順序入れ替えへの耐性)
- 手で網羅できない組み合わせ(アイテム、クラフトなど)

判断基準は「そのバグは遊んですぐ気づけるか」。気づけるなら書かない。

テストを書く場合は、**実装より先に書いてコミットし、失敗を確認する**。
実装のコミットでテストを変更しない。

## 欄を増やすとき

「この欄がなかったせいでAIが誤読したか」が唯一の基準。
同じ種類の誤読が繰り返されたときだけ足す。使われない欄は消す。
