# feat — 振る舞いが増える・変わる変更

## 手順

1. 対象システムの `docs/systems/<id>.md` を読む(なければ新規作成)
2. 仕様書を書く・更新する
3. **人間の確認を待つ**(ここで止まる)
4. 実装する
5. コミットする

## 仕様書の形式

```markdown
---
id: hunger
files: [Hunger*.cs]
touches: []
tunables: HungerConfig
---
## 体験の意図
探索を急かす圧力。即死はさせない。
## デフォルトと違う点
- 空腹0でも移動速度は落とさない
## 相互作用
- WHILE 睡眠中、空腹の減少は半分
## やらないこと
- 食料の腐敗
## 未決
- 空腹0が続いたときの最終ペナルティ
## 確認
- 状態: 空腹10・食料なし・拠点から遠い
- 見るもの: 帰るか進むかで迷うか
## 調整値
- 減少速度(初期 1/分、範囲 0.5〜3)
```

### frontmatter

| キー | 内容 |
|---|---|
| `id` | ファイル名と一致させる |
| `files` | Domain直下の対応ファイル。globで書く |
| `touches` | `save` / `net` / `settings` のうち触るもの。実装前は予定 |
| `tunables` | ScriptableObjectの型名。なければ省略 |

### 各欄の書き方

**体験の意図** — プレイヤーに何を感じさせるか。人間がプレイで判定する基準であり、
書かれていない部分をAIが決めるときの判断基準にもなる。これがあるから自明な振る舞いを書かずに済む。

**デフォルトと違う点** — 普通に実装するとこうなる、という想定からズレる部分だけ。
「上限を超えない」のような自明な振る舞いは**書かない**。

**相互作用** — 他システムとの関係。状態を持つ場合はEARS記法で書く。

- `WHILE <状態>、<振る舞い>`
- `WHEN <イベント>、<応答>`
- `IF <条件> THEN <応答>`

**影響を受ける側のファイルに書く。** 「睡眠中は空腹の減りが半分」は hunger.md に書く。
両方に書くとズレる。

**やらないこと** — 誤読は「書かれていないことまでやる」方向で起きやすいので、境界を明示する。

**未決** — 指示から決まらないことを推測で埋めず、ここに落とす。
「任意」(AIが決めてよい)と「未決」(人間が決める)を区別すること。
未決の項目は仮実装で止め、人間の判断を待つ。未決が多すぎるなら指示が粗すぎる合図。

**確認** — 人間が30秒で判定できるようにする。実装時はこの状態に飛べるデバッグ用プリセットも作る。

**調整値** — ScriptableObjectに出す値と初期値・範囲。**テストで固定しない**(プレイしながら変えるため)。

## 解釈の根拠を併記する

仕様書を書いたら、各欄について「元の指示のどこから、どう解釈したか」を
**チャット上で**報告する(仕様書本文には書かない)。

人間はこれを読んで、自分の意図と突き合わせる。仕様書を読み合わせるだけだと、
AIの誤読がそのまま通る。

## テスト

書くのは以下のみ。それ以外は書かない。

- セーブデータの互換性
- サーバー権威ロジック(クライアント入力の検証、重複・順序入れ替えへの耐性)
- 手で網羅できない組み合わせ(アイテム、クラフトなど)

判断基準は「そのバグは遊んですぐ気づけるか」。気づけるなら書かない。

テストを書く場合は、**実装より先に書いてコミットし、失敗を確認する**。
実装のコミットでテストを変更しない。

## 欄を増やすとき

「この欄がなかったせいでAIが誤読したか」が唯一の基準。
同じ種類の誤読が繰り返されたときだけ足す。使われない欄は消す。
