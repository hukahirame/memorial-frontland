# fix — 不具合の修正

## 原因を分類する

修正する前に、原因が次のどちらかを判定し、**チャット上で人間に報告する**。
人間が見るのはこの分類だけ。コードは見ない。

### A. 実装が仕様に反していた

仕様書は変更しない。実装だけ直す。

### B. 仕様が曖昧で、AIが誤読した

仕様書に1行足してから実装を直す。同じ誤読が再発するため、
実装だけ直しても意味がない。

Bが繰り返し出るなら、仕様書の欄を増やす判断材料になる
(`feat.md` の「欄を増やすとき」を参照)。

## 手順

1. 原因を分類して報告する
2. Bの場合、仕様書を更新する
3. 修正する
4. コミットする

## 再現テスト

「そのバグは遊んですぐ気づけるか」で判断する。

- **すぐ気づけるバグ** — テストを書かない。同じバグが再発しても、また遊べば気づく。
- **静かに壊れるバグ**(セーブ、通信、組み合わせ) — 再現テストを書く。
  修正前に書いて失敗を確認し、修正後に通ることを確認する。

## 既存テストを緩めない

修正のために既存テストの期待値を書き換えたり、ケースを削除したりしない。
既存テストが落ちるなら、それは仕様が変わったということ。
`feat` として仕様書を更新してから進める。

やむを得ない場合は、コミットメッセージに理由を書く。

```
Test-Change: <理由>
```

## 型・依存の問題だった場合

同じ種類のバグを第1層(コンパイル)で防げないか検討し、
可能なら別コミットで Analyzer を追加する。
