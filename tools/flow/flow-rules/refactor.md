# refactor — 振る舞いが変わらない変更

## 不変条件

このコミットで以下が変わってはいけない。これが守られるからこそ、
人間がコードを読まずに済む。

- `docs/systems/*.md`(仕様書)
- 既存テストの期待値
- 既存の公開API(消える・変わる場合は人間の承認が必要。足すのは自由)

いずれかが変わるなら、それは refactor ではない。種別を分けてコミットし直す。

**テストを足すのは refactor に含めてよい。** Legacy から規則を抜くと、その規則を
留めるテストが同時に生まれる。型がまだ無い時点ではテストはコンパイルも通らないので、
先に書いて落とすことができない。足すテストは、いまの振る舞いをそのまま写したものに限る。
期待値を新しく決めたなら、それは refactor ではない。

## 手順

1. 変更前にテストが通ることを確認する
2. リファクタする
3. テストが通ることを確認する
4. コミットする

コミットのとき `dotnet test` がもう一度走り、落ちると REFACTOR-RED で止まる。
テストは作業ツリーを見るので、`.cs` と `docs/` と `tests/` の変更はすべてコミットに入れる。
Unity 側（Game / Legacy のコンパイル、EditMode / PlayMode）は走らない。3 で確かめる。

## 途中でバグを見つけたら

**リファクタを中断する。**

1. 現在の変更を退避する(`git stash`)
2. バグ修正だけを `fix` としてコミットする
3. 退避を戻してリファクタを再開する

「ついでに直す」をすると、振る舞いが変わらないという保証が消え、
このコミットで検証できるものが何もなくなる。

## 既存の公開APIが消える・変わる場合

`docs/public-api.txt` が Domain の公開している面の一覧で、`dotnet test` が作り直す。
1行が1つの面で、static や out や get / set まで含む。使う側が通らなくなる変化は、
既存の行が消えるか書き換わる形で差分に出る。

- 型やメンバを足すだけなら行が増えるだけで、承認は要らない
- 既存の行が消えた・書き換わったら、承認が要る
- 既存の型に abstract の行が増えたら、承認が要る。interface にメンバを足すと実装する側がすべて壊れる

承認が要る差分は**チャット上で人間に提示し、承認を待つ**。
人間が見るのはここだけ。実装は見ない。

承認が取れたら、理由を添えてコミットする。無いと API-CHANGED で落ちる。

```
Api-Changed: <理由>
```

## 仕様書は1文字も変えない

`docs/systems/` の文が変わると REFACTOR-DIRTY で落ちる。
仕様書は関心事のフォルダを指しており、フォルダの中でファイルを移動・リネームしても書き換える必要は無い。

仕様書が `` `SpawnRule.SuppressProgress` `` のようにバッククォートで名指ししたものを移したら、
その名前だけを書き換える。コード名の差し替えだけなら通る。移した先が実在するかは
`SpecConformanceTests` が見る。名前以外の文まで直すことになったら、振る舞いの主張が変わっている。

振る舞いが変わったなら feat か fix。種別を分けてコミットし直す。

どうしても同じコミットに入れるなら、理由を添えて解除する。

```
Spec-Changed: <理由>
```

使ったら、なぜ refactor のままでよいのかがレビューで問われる。

## テスト

新規に書かない。既存テストを通すだけ。

テストが落ちたら、リファクタが振る舞いを変えている。
テストを直すのではなく、実装を直す。
