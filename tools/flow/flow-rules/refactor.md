# refactor — 振る舞いが変わらない変更

## 不変条件

このコミットで以下が変わってはいけない。これが守られるからこそ、
人間がコードを読まずに済む。

- `docs/systems/*.md`(仕様書)
- 既存テストの期待値
- 公開API(変わる場合は人間の承認が必要)

いずれかが変わるなら、それは refactor ではない。種別を分けてコミットし直す。

**テストを足すのは refactor に含めてよい。** Legacy から規則を抜くと、その規則を
留めるテストが同時に生まれる。型がまだ無い時点ではテストはコンパイルも通らないので、
先に書いて落とすことができない。足すテストは、いまの振る舞いをそのまま写したものに限る。
期待値を新しく決めたなら、それは refactor ではない。

## 手順

1. 変更前にテストが通ることを確認する
2. リファクタする
3. テストが通ることを確認する
4. コミットする

## 途中でバグを見つけたら

**リファクタを中断する。**

1. 現在の変更を退避する(`git stash`)
2. バグ修正だけを `fix` としてコミットする
3. 退避を戻してリファクタを再開する

「ついでに直す」をすると、振る舞いが変わらないという保証が消え、
このコミットで検証できるものが何もなくなる。

## 公開APIが変わる場合

増減した公開メンバの一覧を**チャット上で人間に提示し、承認を待つ**。

人間が見るのはここだけ。実装は見ない。

PublicApiAnalyzers はまだ入っていないので、いまは手で挙げる。
入れたら承認ファイルの差分に置き換える。

## ファイルを移動・リネームした場合

対応する仕様書の `files` を更新する必要がある。
ただし `files` の変更は仕様の変更ではないので、REFACTOR-DIRTY には該当しない
(frontmatterのみの変更は許容される)。

本文が変わったら refactor ではない。

## テスト

新規に書かない。既存テストを通すだけ。

テストが落ちたら、リファクタが振る舞いを変えている。
テストを直すのではなく、実装を直す。
