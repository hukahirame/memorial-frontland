# refactor — 振る舞いが変わらない変更

## 不変条件

このコミットで以下が変わってはいけない。これが守られるからこそ、
人間がコードを読まずに済む。

- `docs/systems/*.md`(仕様書)
- 既存テストの期待値
- 公開API(変わる場合は人間の承認が必要)

いずれかが変わるなら、それは refactor ではない。種別を分けてコミットし直す。

**テストを足すのは refactor に含めてよい。** Legacy から規則を抜くと、その規則を
留めるテストが同時に生まれる。型がまだ無い時点ではテストはコンパイルも通らないので、
先に書いて落とすことができない。足すテストは、いまの振る舞いをそのまま写したものに限る。
期待値を新しく決めたなら、それは refactor ではない。

## 手順

1. 変更前にテストが通ることを確認する
2. リファクタする
3. テストが通ることを確認する
4. コミットする

## 途中でバグを見つけたら

**リファクタを中断する。**

1. 現在の変更を退避する(`git stash`)
2. バグ修正だけを `fix` としてコミットする
3. 退避を戻してリファクタを再開する

「ついでに直す」をすると、振る舞いが変わらないという保証が消え、
このコミットで検証できるものが何もなくなる。

## 公開APIが変わる場合

`docs/public-api.txt` が Domain の公開している面の一覧で、`dotnet test` が作り直す。
面が変われば差分に出る。

その差分を**チャット上で人間に提示し、承認を待つ**。
人間が見るのはここだけ。実装は見ない。

承認が取れたら、理由を添えてコミットする。無いと commit-msg が API-CHANGED で落とす。

```
Api-Changed: <理由>
```

## 仕様書は1文字も変えない

`docs/systems/` に差分があると、commit-msg フックが REFACTOR-DIRTY で落とす。
仕様書はスライスを指しており、ファイルを移動・リネームしても書き換える必要は無い。
対応付けは `docs/slices.txt` が持っている。

振る舞いが変わったなら feat か fix。種別を分けてコミットし直す。

どうしても同じコミットに入れるなら、理由を添えて解除する。

```
Spec-Changed: <理由>
```

使ったら、なぜ refactor のままでよいのかがレビューで問われる。

## テスト

新規に書かない。既存テストを通すだけ。

テストが落ちたら、リファクタが振る舞いを変えている。
テストを直すのではなく、実装を直す。
