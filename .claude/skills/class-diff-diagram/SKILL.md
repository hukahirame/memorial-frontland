# クラスの構造の差分を図にする

git diff は行の増減しか見せない。「RootsManager を参照しなくなった」は
消えた行の中に埋もれて読み取れない。そこを図で埋める（[D-009]）。

## 走らせる条件 🎯

**依存グラフが動く変更をしたとき。** 具体的には次のいずれか。

- 型を追加した、削除した、改名した
- フィールド・プロパティ・引数・戻り値の型を変えた
- 型を Legacy から Domain / Game へ移した
- static 参照の張り替え

上のいずれかを含む変更をコミットする前に必ず走らせる。

## 走らせない条件 🚫

- メソッドの本体だけを変えた（呼ぶ相手の型が変わっていない）
- テストだけを足した
- コメント・文字列・書式だけを直した

依存が動いていなければ差分は空になり、**ファイルは作られない**。
空の図が溜まると読む気が失せるため、意図的にそうしてある。

## 手順 🔧

```
dotnet test tests/Domain.Tests/Domain.Tests.csproj   # 素データを更新（1回目は失敗するのが正常）
dotnet test tests/Domain.Tests/Domain.Tests.csproj   # 緑を確認
./tools/diagram-diff.ps1 -Name <slug>                # 差分図を出す
```

出た図を読み、`docs/dependencies-diagrams/` の該当スライスを手で直す。
直したら `dotnet test` をもう一度走らせ、`SliceDiagramTests` が緑になることを確認する。

比較元のコミットにまだ素データが無い場合は、その版を `git worktree` で別の場所に
展開し、今の `DependencyGraphTests.cs` と最小の csproj だけを持ち込んで走らせると
土台が作れる。`-BaseFile <その graph.txt> -Ref <コミット>` で渡す。

## ファイル名 📄

```
docs/dependencies-diff-diagrams/YYYY-MM-DD-<slug>.md
```

- `<slug>` は変更の主題。kebab-case（`roots-registry`, `quest-log`）
- **コミットハッシュを使わない。** amend と squash で変わる
- 日付を先頭に置く。ディレクトリの並びが時系列になる
- 1つの変更単位で1枚。同じ作業を続けているなら同じ名前に上書きする

## 差分図の記法 📐

`graph LR` を使う。`classDiagram` ではない。**すべて実測で確認済み。**

| 軸 | 記法 | 意味 |
|---|---|---|
| 辺の色 | 緑 `#137333` / 赤 `#c5221f` / 橙 `#b06000` / 灰 `#9aa0a6` | 増えた / 消えた / 種類が変わった / 変わらない |
| 辺の線種 | `==>` 太線 3.5px / `-.->` 点線 1px | 関連（フィールドで保持）/ 依存（signature に出るだけ）|
| 辺のラベル | `✚` / `✖` / `⟳` | 増減と種類変化。色が読めない環境の保険 |
| 箱の枠 | 緑4px / 赤4px点線 / 灰1px | 現れた型 / 消えた型 / 元からある型 |
| 箱の塗り | 白で統一 | 中の色付き文字と競合させない |
| メンバの文字色 | 緑 / 赤 / 橙 / `#202124` | 追加 / 削除 / 変更 / 変化なし |
| 区切り線 | `___` の行、`#5f6368` | 名前 / 属性 / 操作 の3区画 |
| 囲み | `subgraph` | 層 |
| 可視性 | `+` `-` `#` `~` のあと**半角スペース** | `+ int Progress` |

### なぜ classDiagram ではないか

`classDiagram` はメンバの区画と可視性の解釈を持つ代わりに、**辺の色も太さも
指定できない**（`linkStyle` が無く、`themeCSS` による回避は描画側の
`securityLevel` に止められることを実測で確認）。

変化と関係の種類は別の軸に置きたい。`classDiagram` だと線種1つに両方を
載せることになる。`graph LR` なら色と線種に分けられるので、そちらを採った。

代償はメンバの区画が無いこと。`___` の行で代用し、可視性はただの文字にする。

### 描画で踏んだ罠

いずれも一度壊してから分かったもの。**外すと再発する。**

| 罠 | 対処 |
|---|---|
| `classDef` の `color:` が `!important` でラベル内の `span` を潰す | `classDef` には `fill` と `stroke` だけ書く |
| ラベルは `["..."]` で囲むので、中の `"` でラベルが閉じる | `style` の引用符はシングル |
| `<` `>` は HTML のタグと解釈される | 描画時に `&lt;` `&gt;` へ逃がす。素データは C# のまま |
| span で包まない行はテーマ既定色になり灰色に見える | **全ての行**を包む。メンバの無い箱の名前も |
| `linkStyle` は添字で辺を指す | 辺は 追加 → 削除 → 種類変化 → 不変 の順に出す |
| 区切り線が固定長だと短くて区切りに見えない | その箱の最長行の文字数に合わせる |

### 出すもの

- 変化に触れている型だけ。全体図ではない
- 既存の型は**変わったメンバだけ**。全部出すと読めない
- 丸ごと現れた型・消えた型は**全メンバを色なしで**。
  何が増えたかではなく「その型が何を提供するか」が読みたいため
- 戻り値が `void` の操作は戻り値を書かない。過半数が `void` で情報にならない
- 変化した型どうしの変わっていない辺は灰の細線で添える（位置関係のため）

## アルゴリズム ⚖️

**ここが正典。**実装（`DependencyGraphGenerator.cs` と `diagram-diff.ps1`）は
この写し。食い違ったら実装を直す。
正規表現そのものは書かない。読めないし、意味が変わらない書き換えで嘘になる。

### 第1部 抽出 — ソースから素データへ

**入力** 次の3か所の `.cs` を、ファイル名の昇順で読む。

```
Assets/_Project/Scripts/Domain    層 Domain
Assets/_Project/Scripts/Game      層 Game
Assets/LegacyScripts              層 Legacy
```

**1. 前処理** 文字単位で走査し、行コメント・ブロックコメント・文字列リテラル
（逐語 `@"..."` を含む）・文字リテラルを取り除く。**改行は残す。**
以降の判定は、この除去後の本文に対して行う。

**2. 波括弧の深さを追う** 1行ずつ処理し、行の中の `{` `}` で深さを増減する。

- 型宣言（`class` / `struct` / `enum` / `interface` と識別子）を見たら**保留**する
- `{` で深さを1増やす。保留があれば、その深さで**その型を開いた**と記録し、保留を消す
- `}` でその深さに開いている型を閉じ、深さを1減らす
- **型が開いている深さと同じ深さの行**だけがメンバの候補。これで局所変数を除く

**3. メンバの判定** 候補の行に対し、次の順で試す。最初に当たったものを採る。

1. 先頭の属性 `[...]` を（連続していても）除去する
2. `enum` の中なら、`名前` あるいは `名前 = 値` の形だけを値として拾う
3. **コンストラクタ** — 修飾子の並びの直後が「その型と同じ名前」＋`(`
4. **一般形** — `修飾子* 型 名前` の直後が `(` `=>` `=` `;` `{` のいずれか
   - `(` なら**操作**。引数は最初の `(` から最初の `)` まで。
     深さ0のカンマで分割し、`ref` `out` `in` `params` `this` を落として型だけ採る
   - それ以外なら**属性**
5. **括弧が次の行にあるプロパティ** — 行が名前で終わるもの。属性として扱う

   ```csharp
   public IReadOnlyList<Root> All      // ここで行が終わる
   {                                   // 判定用の記号が次の行
   ```

   このプロジェクトは括弧を次行に置くので、これが無いとプロパティが系統的に漏れる。
   実測で再現率が 93.3% から 100% に上がった。型の直下の深さでしか見ていないので、
   `return x` のような文とは衝突しない

**4. 可視性** 修飾子から決める。無ければ `private`。

```
public → +      protected → #      internal → ~      それ以外 → -
```

**`[SerializeField]` が付いていれば `+`。** コードには private だが Inspector には
公開されており、外から供給される点で public と同じ。`_Project` では public 可変
フィールドを禁じている（[D-007]）ので、移行が進めば `+` のフィールドは
SerializeField か ScriptableObject だけになる。専用の印は付けない。

**5. 表示形式** 総称の `<` `>` は `~` に置き換える（mermaid が山括弧を扱えないため）。

```
属性            <可視性> <型> <名前>              + int Progress
操作            <可視性> <名前>(<引数型, ...>)     + Calm(int)
操作（戻り値あり） 上に ` <戻り値型>` を足す         + Find(string) Root
コンストラクタ   <可視性> <型名>(<引数型, ...>)     + Root(string, int)
enum 値         <名前>                            Stampede
```

- 可視性の記号のあとに**半角スペース**を1つ置く
- **戻り値が `void` なら書かない。** 過半数の操作が `void` で情報にならない
- **総称の山括弧はそのまま `<` `>` で持つ。** HTML へ逃がすのは描画側の仕事

**6. 辺** 型ごとに2つの集合を作る。

```
保持 assoc   属性の型、およびその総称引数
使用 dep     操作の引数型・戻り値型、およびその総称引数
```

続いて**本体参照**を足す。各ファイルについて、既知の型名を単語境界で検索し、
見つかったら**そのファイルが宣言する全ての型**から `dep` を張る。
メソッドの中の参照は型ごとに分けられないので、ファイル単位になる。

最後に、**同じ組に `assoc` があれば `dep` は出さない**。保持の方が強い関係のため。
自己辺と、既知でない型への辺は出さない。

**7. 出力** `docs/dependencies-diagrams/graph.txt`。節ごとに行が並ぶ。

```
[types]     <型> <層> <種別>
[cofile]    同一ファイルに宣言された型を空白区切りで（2つ以上のときだけ）
[edges]     <From> -> <To> <assoc|dep>
[members]   <型>|<メンバ名>|<表示>
```

型名で昇順に並べる。並びが安定していないと diff が読めない。

### 第2部 比較 — 素データから図へ

**入力** 新旧の `graph.txt`。辞書は**必ず序数比較**にする。
PowerShell の `@{}` は大文字小文字を区別せず、`roots` と `Roots` が同じ鍵になる。

**1. 型** 名前の差集合。現れた型と消えた型。

**2. 辺** `A|B` の鍵の差集合で増減を取る。加えて、**両側にあって種類が違う辺**を
「種類変化」として別に数える。「引数で使うだけだった型をフィールドで持つように
なった」は状態の移動そのものなので、増減とは別に橙の1本で示す。

**3. メンバ** 型ごとに決める。

- **丸ごと現れた型・消えた型** — 全メンバを状態なしで並べる。
  何が増えたかではなく「その型が何を提供するか」が読みたいため
- **それ以外** — メンバ名ごとに、新旧の表示文字列の集合を比べる
  - 片方にしか無いものが**新旧ちょうど1つずつ** → `変更`（新側の表示を使う）
  - それ以外 → `削除` と `追加` を別々の行に出す

1つずつのときだけまとめるのは、オーバーロード（`Inventory.Add` が2つある）で
対応付けを誤らないため。

**4. 図に出す型** 次の和集合。

```
増えた辺・消えた辺の両端  ∪  現れた型  ∪  消えた型  ∪  メンバが動いた型
```

**5. 描画順** `linkStyle` は添字で辺を指すので、**順序が意味を持つ**。

```
1. subgraph  層は Domain → Game → Legacy、型は名前の昇順
2. 辺        増えた → 消えた → 変わっていない
3. linkStyle 上の3群にそれぞれ色
4. classDef  現れた型と消えた型の箱の色
```

変わっていない辺は、**両端とも図に出ている型のとき**だけ添える。位置関係のため。

**6. ノードラベル**

```
<型名>
<区切り>
<属性の行...>
<区切り>
<操作の行...>
```

区切りは**その箱の中で最も長い行の文字数**ぶんのアンダースコア。固定長だと
短くなりがちで区切りに見えない。長さは色付けの `<span>` を外した表示部分で測る。
空の区画には区切りを出さない。

**7. 色** 行は `<span style='...'>` で包む。**引用符は必ずシングル。**
ラベルは `["..."]` で囲まれるので、中にダブルクォートがあるとそこで
ラベルが閉じたと解釈されて図が崩れる。

**8. 変化がゼロならファイルを作らない。** 空の図が溜まると読む気が失せる。

### 精度の測り方

Domain 層だけは**リフレクションという独立した正解**がある
（`DomainDiagramTests` が `docs/domain-class-diagram.md` を型から生成している）。
字面解析の結果と突き合わせれば、取りこぼしと誤検出を数えられる。

```
公開メンバを両方から集める
  正解  domain-class-diagram.md の class ブロック
  実測  graph.txt の [members] のうち Domain 層かつ + で始まるもの
可視性の後の空白、void、総称の記法、static の $ を揃えてから比較する
```

**2026-08-28 時点で再現率 100%（45件）、誤検出 0。**
コンストラクタは正解側の図が出していないだけなので数から除く。

Legacy と Game には正解が無い。リフレクションが使えないことが
字面解析を選んだ理由そのものなので、そこは測れない。
**抽出器を変えたら必ずこの測定をやり直すこと。**

### 盲点

- `var` で受けている依存は型名が字面に現れないので出ない
- 同一ファイルに宣言された型どうしには辺が出ない。`[cofile]` 節が補う
- 複数行にまたがる宣言は拾えない
- `partial` は分割されたファイルごとに別々に見える
- 本体参照はファイル単位。1ファイル複数型のときは実際より多く出る

## 現状図の書式 📊

`docs/dependencies-diagrams/` は差分図とは形を変える。**`graph LR` の箱のまま**、
メンバを載せない。全体像を掴むためのもので、メンバが載ると1枚に収まらなくなる。
変化の軸を持たないので、上の記法のうち色と記号が遊ぶ。用途が違うので形も違う。

- 1ファイル1機能スライス。ファイル名は機能の英語 kebab（`inventory.md`）
- 冒頭に HTML コメントで「手で維持する」ことと更新手順
- `# <日本語の機能名> <絵文字>`、その下に1〜2行の説明
- Domain と Game は `subgraph` で囲み、Legacy は素で置く
- 図のあとに2〜4行の補足。なぜこの形か、どのスライスと接するか
- **1枚10型まで。** 超えたら切り直す（[D-009] の検出条件）

Legacy は主役ではない。Domain / Game に触れている分だけ境界として置く。

## 検査 ✅

現状図は手で維持するので腐る。腐り方を2つだけ機械が見張る。

| テスト | 何を見るか |
|---|---|
| `スライス図に実在しない依存が描かれていない` | 図がコードについて嘘をついていないか |
| `DomainとGameの型がどれかのスライスに出ている` | 新しい型を図に入れ忘れていないか |

**どう切るかは見ない。** 何を1枚にまとめるかは人の判断で、機械が正解を持てない。

## 素データの限界 ⚠️

`docs/dependencies-diagrams/graph.txt` はソースの字面から作る。Legacy は
UnityEngine 依存でリフレクションが使えないため。

- `var` で受けている依存は型名が現れないので出ない
- 同一ファイルに宣言された型どうしには辺が出ない（`AddResult` は `Inventory.cs` にある）。
  `[cofile]` 節がそれを補う。知らないと検査が誤判定する
- フィールドと局所変数は波括弧の深さで区別する。フィールドは必ず型が明示されるので
  （`var` フィールドは書けない）、一般の参照検出より確実に取れる
