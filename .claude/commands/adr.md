このセッションを振り返り、`docs/DECISIONS.md` について (1) 実態と食い違った採用中の ADR、(2) 新しく起票する候補を挙げる。
$ARGUMENTS が指定されている場合は、その話題に絞る。

## 手順

1. `grep -n "^## \[D-\|^status:\|^scope:" docs/DECISIONS.md` で見出しと status と scope を取る。
2. `status: Proposed` の項目があれば、最初に「保留中: D-XXX（タイトル）」の形で 1 行ずつ示す。なければ何も言わない。
3. **見直し。** `git status --short` と、このセッションで変えたファイルを、採用中（Accepted）の ADR の scope と突き合わせる。
   重なる ADR だけ全文を読み、このセッションの変更が **決定** と食い違っていないかを見る。食い違っていれば、次のどちらかを候補にする。
   - 選び直さずにやめた → `Retired（理由 1 行）`
   - 別の案を選び直した → 新しい ADR を書き、古い方を `Superseded by [D-YYY]`
   一部だけ古くなったなら、status の後ろに括弧で書く案にする。
4. **起票。** このセッションの会話から、下の「候補にする条件」をすべて満たす判断だけを抜き出す。
   会話が短い場合のみ `git log --oneline -10` を補助的に見てよい。
5. 見直しと起票の候補を示し、AskUserQuestion で採否を尋ねる。**承認を得るまで `docs/DECISIONS.md` を編集しない。**
6. 承認されたものを反映する。起票は末尾に足す。見直しは status（と、道が消えたなら scope）だけを直し、本文は書き換えない。
   廃止・置き換えにした ADR を仕様書・規約・CLAUDE.md・コードが `[D-XXX]` で指していたら、その ID を外す。

## 候補にする条件

次をすべて満たすもの。1 セッションで 0 件が普通で、多くても 1〜2 件。

- プロジェクト全体、または複数の仕組みにかかる
- 戻すのが高くつくか、エージェントが知らずに逆へ直しそうである
- 却下した案と、その理由を書ける

## 候補にしないもの

該当するものは、単に挙げない。行き先の提案や、新しい仕組みの提案はしない。

- 1 つの仕組みの中で済む決定（その仕様書 `docs/systems/` に振る舞いとして書く。理由は残さない）
- 道具やエンジンの落とし穴と、その対策（`FRICTIONS.md`）
- 代償なしに明らかに良い方（バグ修正、タイポ、素直なリファクタリング）
- 後から容易に変更できる実装の詳細
- 既に DECISIONS.md に同趣旨の記載があるもの
- 命名・書式・フォーマット
- 既知の不具合、ツールの一時的な挙動

## 品質基準

**却下案とその理由を書けない候補は挙げないでください。**
比較も代償も発生していない判断は、判断ではなく既定値です。

却下理由は、その場限りではなく**新しいケースにも一般化する形**で書くこと。
- 悪い例: 「今回は不要だったため」
- 良い例: 「6人規模では暗黙的解決の見通しの悪さが学習コストを上回るため」

**決定** に数・クラス名・ファイルの道を書かない。それらはコードと仕様書が持ち、変わったときに ADR が嘘になる。
決定は、それを覆すときにしか変わらない粒度で書く。

## 出力形式

起票の候補ごとに以下を提示する。ID は既存の最大値 + 1。欠番・再利用はしない。追記先は末尾。書式やMDを勝手にアレンジしない。

```
## [D-XXX] （命令形のタイトル。何をするか）
status: Accepted
date: YYYY-MM-DD
scope: この決定が効いている道。glob 可

**背景** — 何が問題だったか。既に固定されていた制約。
この節だけで状況が再現できること。決定から自明な場合は省略してよい。

**検討した選択肢** —
(a) 却下した案。→ 却下。理由（一般化した形で）
(b) 却下した案。→ 却下。理由

**決定** — 命令形で1〜2段落。禁止事項があれば明示的に名指しする。
例: 「Domain は UnityEngine を参照しない」

**帰結** — 新たに発生する作業、明確に困難になること、
判断が誤りだった場合の検出条件。無ければ省略。
```

見直しの候補は、ADR の ID とタイトル、食い違った所（何を変えたか）、新しい status の案を 1 件 3 行ほどで示す。

## 採否の確認

候補を提示したあと、AskUserQuestion で採否を尋ねる。
候補1件につき1問。質問文には D-XXX のタイトルを入れ、どの候補への問いか分かるようにする。

起票の選択肢:
- **起票** — `status: Accepted` として追記する
- **保留** — `status: Proposed` として追記する。判断は次回以降に持ち越す
- **破棄** — 何もしない

見直しの選択肢:
- **直す** — 示した status に変える
- **そのまま** — 食い違っていない。何もしない

保留中の項目は次回の `/adr` で必ず一覧に出るため、放置されない。
候補が0件のときは質問しない。

## 候補がない場合

「ADR 候補: なし」とだけ答える。
保留中の項目があればそれだけ示す。無理に挙げない。空振りは正常です。

## 禁止事項

- 会話の要約や作業ログを出さない。候補だけを出す
- 承認を得ずに `docs/DECISIONS.md` を編集しない
- 新しい CI チェック、CLAUDE.md の制約、ドキュメントの追加を提案しない
- `docs/JOURNAL.md` を読まない。却下案や覆された前提が混在しており、採用済みと誤読する
