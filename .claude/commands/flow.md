---
description: 変更の種別を判定し、対応する規則に従って作業を進める
---

作業の前に種別と影響範囲を決めた計画を書き、人間の承認を取ってから作業する。

## 種別の判定

| 種別 | 条件 | 読むファイル |
|---|---|---|
| feat | 振る舞いが増える・変わる | @tools/flow/flow-rules/feat.md |
| refactor | 振る舞いが変わらない | @tools/flow/flow-rules/refactor.md |
| fix | 不具合の修正 | @tools/flow/flow-rules/fix.md |
| tune | ScriptableObjectの値のみ | @tools/flow/flow-rules/tune.md |
| asset | シーン・プレハブ・アセット | @tools/flow/flow-rules/asset.md |
| chore | 仕組み・設定・ツール・文書の変更 | — |

判定が曖昧な場合は、人間に確認してから進める。

テストと文書（`STATE.md`、ADR、仕様書）は、それを変えた理由の種別と同じコミットに入れる。
テストや文書だけを足すときは chore にする。

chore に規則ファイルは無い。差分の形だけ下の表の判定が見る。
規則を書くのは、同じ迷いが2回出たときにする。

## 1コミット1種別

複数の種別が混ざる場合は、コミットを分割する。計画も種別ごとに1枚ずつ書く。

順序: **fix → refactor → feat**

- 修正を先にコミットしておけば、リファクタで壊した場合に切り分けられる
- 「ついでに直す」をしない

## 計画

コードを触る前に、規則ファイルを基に計画を書く。1枚が1コミットになる。
`.flow/` に置き（追跡しない）、中身をチャットに貼って承認を待つ。

```markdown
# refactor: 敵の湧きの規則を Domain へ出す

種別: refactor

## 範囲

- enemy
  - Assets/LegacyScripts/Enemy/Slime.cs
  - Assets/_Project/Tests/Domain/SpawnRuleTests.cs
- その他
  - docs/systems/enemy.md

## やること

## 変えないもの

## 確かめ方
```

- **件名** — 最初の `# ` の行。そのままコミットの件名になる
- **範囲** — 変える・消す既存ファイルを、字下げした箇条書きで道のまま書く。字下げしない行は人間向けの見出しで、関心事の名前か「その他」。
  足す新しいファイル、`STATE.md`、生成物（先頭に「手で編集しない」）、書いた道の `.meta` は書かなくてよい。
  移動は元の道も書く
- **変えないもの** — 規則ファイルの不変条件のうち、この作業で効くもの
- feat は仕様書の変更案を文面ごと入れ、各欄の解釈の根拠をチャットに添える（`feat.md`）

人間が承認したら、書いた順に渡す。この実行は許可ダイアログで止まる。

```
sh tools/flow/flow approve .flow/01-fix.md .flow/02-refactor.md
```

**作業中に計画とずれたら止まる。** 範囲に無いファイルを触る必要が出た、種別が変わる、などは
計画を直してチャットで提示し、承認を取り直して `flow approve` し直す。残っている計画ごと置き換わる。

承認済みの計画は `.git/flow/active/` にあり、そこを読んで作業する。
使い終わった計画は `docs/plans/` に移る。そこは読まない（CLAUDE.md）。
作業をやめて計画を捨てるのは人間が決める（`sh tools/flow/flow cancel`。許可ダイアログで止まる）。

## コミット手順

```
git add -A
git commit -m "<計画の件名>

Change-Type: <計画の種別>"
```

- `Change-Type:` トレーラーはちょうど1行必須。commit-msg フックが先に検証する。
- ブランチに載る直前に、reference-transaction フックが `tools/flow/flow verify` を
  呼び、宣言と、宣言した種別とコミットの差分を突き合わせる。amend でも `--no-verify` でも走る。
- 承認済みの計画が残っているあいだは、先頭の計画とも突き合わせる。通ったらその計画を使い終わったことにする。
- `git revert` が作るメッセージには宣言が無く落ちる。`--no-commit` で戻してから種別を書いてコミットする。

| 判定 | 落ちる条件 | 解除 |
|---|---|---|
| CHANGE-TYPE | `Change-Type:` がちょうど1行でない、または許す種別でない | 無し |
| PLAN-TYPE | 種別が先頭の計画と違う | 無し |
| PLAN-MESSAGE | 件名が先頭の計画と違う | 無し |
| PLAN-SCOPE | 計画の範囲に無い既存ファイルが変わった・消えた | 無し |
| REFACTOR-DIRTY | refactor で `docs/systems/` の文が変わった。バッククォートで囲んだコード名の差し替えだけなら通る | 無し |
| REFACTOR-RED | refactor で `dotnet test` が通らない。テストが読むものが作業ツリーとコミットで違う | 無し |
| API-CHANGED | refactor で `docs/public-api.txt` の既存の行が消えた。既存の型に abstract の行が増えた | `Api-Changed: <理由>` |
| TEST-CHANGED | feat 以外で、既存テストの行が消えた・書き換わった、ファイルが消えた、`Ignore` などテストを止める行を足した。足すのと中身そのままの移動は通る | `Test-Changed: <理由>` |
| TUNE-CODE | tune で `*.cs` が変わった | 無し |
| CHORE-CODE | chore で `Assets/`（`Assets/_Project/Tests/` を除く）が変わった | 無し |

  解除トレーラーは人間の承認と対になる判定にだけ置く。`Api-Changed:` と `Test-Changed:` は、
  出力が示す差分をチャットで提示して承認を取るまで足さない。両方要るときは一度に承認を取る。
  残りは種別を変えるかコミットを割るのが正しい直し方で、逃げ道を作ると自分で足して通してしまう。
- **`--no-verify` は使わない。**
- PLAN-* 以外で落ちたら、出力の指示に従って修正し、再度コミットする。人間に確認を求めない。
- **push はしない。** 人間が打つ。

## 人間が確認する地点

以下の2か所では作業を止めて人間の応答を待つ。それ以外では止めない。

1. **計画を書いた直後** — 範囲と、feat なら仕様書の解釈が合っているか。作業中にずれたときも同じ
2. **動くものができた後** — プレイして判定

## 原則

- 自明なことは仕様書に書かない。AIのデフォルトとズレる部分だけ書く。
- 指示から決まらないことは推測で埋めず、`未決` に落とす。
- 遊べばすぐ気づくバグのためにテストを書かない。
