## 書き方

並びは、全体から細部へ読む順。管理のページ（`.spec/admin.html`。`python tools/spec/build.py` で仕様書から作る）もこの順に並ぶ。

関心事のフォルダを足したら仕様書も足す。忘れると `dotnet test` が落ちる。

仕様書は受け入れ条件。なぜそうするかは書かない。狙いは企画（公開しない。[D-25]）が、案の選び方は設計判断（`docs/DECISIONS.md`）が持つ。

```markdown
---
id: hunger
name: 空腹 🍖
touches: [save]
---

## 用語

- **空腹** — 時間で減り、食べると戻る値

## 受け入れ条件

- 空腹が尽きても移動は遅くならない
- WHEN 食べ物を使った、空腹が戻る（[inventory](inventory.md)）
- WHILE 眠っている、空腹の減りが遅くなる
- IF 空腹が尽きている THEN 体力が自然に戻らない

## やらないこと

- 食料の腐敗

## 未決

- 空腹が尽きたまま続いたときに何が起きるか
```

| 欄 | 書くもの |
|---|---|
| `id` | ファイル名と同じ。関心事のフォルダ名を小文字にしたもの |
| `name` | 表示名 |
| `touches` | `save` / `net` / `settings` のうち触るもの |
| 用語 | その仕組みの言葉の意味と呼び分け。無ければ欄ごと書かない |
| 受け入れ条件 | こう振る舞えば合格、と言える文。いつも成り立つ決まりは地の文で、きっかけは `WHEN`、あいだは `WHILE`、場合は `IF … THEN` で始める |
| やらないこと | 入れない振る舞い。書かれていないことまで作るのを止める |
| 未決 | 人が決めていない振る舞い。推測で埋めずにここへ置き、決まったら受け入れ条件へ移す |

- 壊れたら人が困る振る舞いだけを書く。普通に作ればそうなることは書かない
- 遊んで詰める数（秒・量・割合・値段・しきい値）は書かない。数はコードとデータが持ち、条件は「【抑制】に届いていれば」のように名前で指す。
  作りを決める数（受注は 1 本、根源は 3 つ）は書く
- 作り方（クラス名・ファイルの道・組み立ての手順）は書かない。変えるときに踏む作りの注意と道具の落とし穴は `FRICTIONS.md` に書く
- 同じ条件は 1 か所に書く。ほかの仕組みが絡む条件は、振る舞いが変わる側の仕様書に書き、相手はリンクで指す
- 未決のうち、複数の振る舞いや作りが決まる問いは設計判断にして、番号で指す
