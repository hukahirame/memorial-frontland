**Unity / Pipeline の運用で踏んだこと**

- **Unity のプロセスは `unity pipeline list` の PID で特定する。**
  `Get-Process Unity` の先頭は Editor とは限らず、AssetImportWorker が混ざる。
  今日それで Editor ではないプロセスを kill し、診断も別プロセスに対して行っていた。
- **`run_tests` にクライアント側の短いタイムアウトを付けない。**
  タイムアウトでキャンセルが走ると `PipelineTestRunner.InvalidatePreviousRun` に入り、
  Pipeline が実行ゲートを握ったまま CPU を空回りさせる。以降のコマンドは全部タイムアウトする。
  長時間かかる可能性があるコマンドはバックグラウンド実行にする。
- **フリーズの判定は CPU ではなくログ行数で行う。**
  エディタが非フォアグラウンドだとフレームレートが絞られ、無限ループ中でも CPU がほぼ立たない。
  「CPU 0 なのに Editor.log が毎秒数十行増える」= 低速で回っている、が実際に起きた。
- **`unity open` は Editor を子プロセスとして保持する。**
  バックグラウンド実行にしたコマンドが終了したタイミングで Editor も落ちた。
  CLI から起動するならフォアグラウンドで扱うか、Hub から開く。
- **PowerShell スクリプトは BOM 付き UTF-8 必須。**
  BOM 無しだと 5.1 が CP932 として読み、日本語コメントが壊れて構文エラーになる。
  フックは失敗しても黙って何も起きないため、単体実行で確認しないと気づけない。
  加えてフック経由では git の出力も CP932 になるので `[Console]::OutputEncoding` を明示する。
- **フックとアナライザは「発火すること」まで確認する。**
  最初の `.editorconfig` は `EnforceCodeStyleInBuild` と各診断 ID の severity 指定が無く、
  設定した気になっていただけで何も検出していなかった。
  一時的に違反コードを置いて、実際に警告が出ることを見るまで信用しない。

### 8/25

**Unity 6.3 移行後の初 Play でエディタが停止**

- `SaveSystem.Awake()` がセーブファイルの存在だけを条件に `Load()` を呼び、その中で
  `SceneManager.LoadScene(entered_scene)` を実行する。セーブの `entered_scene` と
  同じシーンで Play すると、遷移先で `Awake` が再入して無限にシーンを読み直す。
- 症状は「フリーズ」に見えるが、実際は低速で回り続けている。エディタが非フォアグラウンドだと
  フレームレートが絞られるため CPU がほぼ立たず、Editor.log だけが 52行/秒 で増える。
  → 固まったように見えたら、CPU 増加ではなく **ログの行数の増加**で判定する。CPU 0 でも動いている。
- 対症療法として「現在のシーンと一致するなら `LoadScene` を呼ばない」ガードを入れた。ループは塞がる。
- 移行とは無関係で、以前から MainSite で Play すれば同じことが起きていたはず。
  Title から始める習慣だったため踏んでいなかった。

**構造的な問題（未着手）**

- `SaveSystem`: 別シーンから遷移する経路では `LoadScene` 直後に `StartCoroutine(Load2())` を
  呼ぶが、遷移で自身が破棄されコルーチンも止まる。`DontDestroyOnLoad` も無い。
  この経路ではセーブが適用されていない可能性が高い。
- そもそも `Awake` から `SceneManager.LoadScene` を呼ぶ設計が危うい。
  起動用シーンがセーブを読んでから遷移する形に作り替えるのが根治。
- ゲーム状態の正典がシーンに散在している。所持金は UI ラベルの文字列を `int.Parse` している。
  `SaveData` はデータモデルではなくシーン走査器で、抽出できるルールが無い。
  → セーブの Domain 分離は「最初」ではなく「最後」。他システムのドメインモデルが先。
- インベントリの `items` / `stocks` / `maxstocks` が並行3リスト。スロット型にまとめるべきだが、
  `SaveData` と Inspector のシリアライズを同時に触るため別スライス扱い。
- シーンに Missing Mono Script が残っている（`Silent Land playerA`、`airsenser`）。
- `PlayerInventory` を `_Project` へ移せない。`Player2` / `GameManager` / `Inventbutton` /

### 8/22

**Git / LFS**

- Git LFS導入確定。UVCSはGitと併用するとまずい。
  1プロジェクトを2リポジトリに割ると、コード変更とアセット変更のアトミックな
  コミットが不可能になり「この時点の状態」を再現できなくなるため。
  UVCS の GitSync（実体UVCS・Gitへミラー）は機能としては成立するが、
  PR / Actions / CODEOWNERS を前提にした現行の設計と噛み合わないため採用しない。
- `.gitattributes` は Unity 標準テンプレート + `*.prefab merge=unityyamlmerge` を追加。
  広く出回っているテンプレートに prefab の行が無い版があるため要注意。
- `unityyamlmerge` は `.gitattributes` の記述だけでは動かない。各マシンで
  `git config merge.unityyamlmerge.driver` の設定が必要で、未設定だと通常の
  テキストマージにフォールバックして YAML が壊れる形で解決される。
  → 全員が設定する必要があるため README のセットアップ節に手順を置く。
  ただしこれは保険であり、本体はシーン / プレハブの担当排他運用。
- `git lfs install` 未実行のまま clone すると、画像がポインタ文字列として展開され
  Unity が壊れたアセットとして扱う。CONTRIBUTING ではなく README 冒頭に置く。
- GitHub の LFS 無料枠は 1GB / 転送 1GB。過去バージョン込みの累積で消費するため
  体感より早く尽きる。バイナリの頻繁な上書きコミットを避ける。
- 素材は「元データ」と「書き出し済み」を分離する。`.psd` / `.blend` / 生録音は
  Assets 外（Drive）、`.png` / `.fbx` / `.wav` と対応する `.meta` のみ Git。
  Assets 配下を追跡から外して手動同期する運用は、GUID が振り直されてシーン /
  プレハブの参照が全損するため不可。
- push 済みの秘密情報は履歴から確実には消せない。filter-repo で書き換えても
  GitHub 側に PR の diff や fork 経由で残ることがある。
  → 消す作業を当てにせず、gitleaks（pre-commit）+ GitHub Push Protection で
  入る前に止める。漏洩時の第一手は履歴書き換えではなく鍵の失効・再発行。

**Unity 6 移行**

- `upgrade/unity6` ブランチで実施し、main は動く状態のまま維持する（ブランチはできればつくらない）。
- 手順: 全ファイルをコミット → ブランチ作成 → `Library/` 削除 → Unity 6 で起動 →
  API Updater → コンソールのエラー解消 → Play / ビルド確認 → main へマージ。
- ProjectSettings と全 `.meta` が書き換わり巨大な差分になるため、アップグレード
  だけで1コミットにする。他の変更と混ぜると後から追えなくなる。
- マージ後は全員が同一バージョンに揃える必要がある。旧バージョンで開くと
  シリアライズ形式が巻き戻るため、マージのタイミングは事前周知。
- Unity CLI / `com.unity.pipeline` は Unity 6 以降が前提。エージェント運用の前提条件。

**エージェント権限（既決だが未記録だった分）**

- シーン / プレハブはエージェント書き込み禁止。理由は2つで、Git で差分レビューが
  できず何をしたか検証不能であること、`.meta` の GUID 破損が起きると参照が全損し
  復旧コストが高いこと。
  → 権限境界の一次基準は「Git で差分レビューできるか」。
- 逆にドメイン層（UnityEngine 非依存）は `dotnet test` で自動検証できるため全面委任可。
  asmdef による層分離が、そのままエージェントの権限境界として機能する。
- 禁止はルールファイルではなく物理で担保する。エージェント用の git worktree を分け、
  そこにシーン / プレハブを置かない。「触るな」と書くより「存在しない」方が確実。
- ルールファイルが守られなくなる典型条件: コンテキストが長い / ルール項目が多い /
  直近の指示と競合する / 検証不能な抽象表現 / タスクに詰まっている。
  特に最後は、テスト削除・`Skip` 付与・asmdef への参照追加などルールを破る方向へ
  逃げたうえで「対処しました」と報告してくる。ルールは多いほど守られなくなる。
- `[CliCommand]` を含む差分は PR で人間承認必須。属性を足すだけでホワイトリストを
  自己拡張できてしまうため。
- Play Mode で domain reload が起きると Pipeline サーバの bearer token が再生成され、
  起動時にトークンを読んだ MCP クライアントが以降 401 で永久に失敗する既知の挙動。
  Play Mode を抜けても回復せず、MCP クライアントの再起動が必要。要バージョン確認。

**公開リポジトリ運用**

- `.gitignore` のホワイトリストは third-party アセットのライセンス回避が目的であり、
  「clone しても Unity で開いて動かない」のは意図した状態。

- 検証は「clone して Unity で開く」ではなく `git ls-files` の目視。third-party が
  含まれないこと、`.cs` / `.asmdef` が欠けていないこと。

※ この日以前に決めた事項をまとめて記録した初期投入

**アーキテクチャ**

- asmdef によるレイヤー分離（ドメイン層 ⇔ プレゼンテーション層）を採用。
  層の依存関係はドキュメントではなく asmdef の references が物理強制する。
  規約として文章で書くと乖離するため、ドキュメント側には意図のみ残す。
- VContainer の導入は見送り、Composition Root パターンで対応。
  6人規模では DI コンテナの学習コストと暗黙的な解決の見通しの悪さが上回る。
  再検討トリガー: 手動配線が破綻したと感じたとき、または参加者が10人を超えたとき。
- レガシーコードは `Assets/Scripts/Legacy/` に隔離し、asmdef 壁で新規コードから
  参照できない状態にする。段階的移行のため一括書き換えはしない。
- 移行方針は「1機能を選んでレイヤー分離＋テスト付きで作り直し、それを雛形にする」。
  全体を先に設計せず、動く実例を1つ作ってから横展開する。

**プラットフォーム・ネットワーク**

- PC / モバイル両対応は、モバイルを性能上限として設計し PC はスケールアップで対応する。
  逆順（PC 基準で作って後からモバイルに落とす）は後戻りコストが大きいため。
- クロスプレイは、アカウント名前空間・プロトコルバージョニング・シリアライゼーション形式を
  最初から互換のある形で実装し、マッチメイキングのプール分離は後から行う。
  互換基盤で作って後から分離するのはほぼコストゼロだが、独立システムで作って
  後からマージするのは移行コストが高く、競合解決が不可能になりうる。
- 同期モデル（リアルタイム vs 非同期）は未決定。アーキテクチャへの影響が大きいため、
  ネットワーク層の実装着手前に決める必要がある。
- 認証はマネージドサービスに委譲し、認可は自分で設計・所有する。
  自前認証の実装は面接リスクであり、責務の切り分けとして説明可能な形にする。

**開発基盤**

- AI エージェントの書き込み権限は `[CliCommand]` ホワイトリスト方式で物理的に制限する。
  AGENTS.md への記述による制限は確率的な遵守にすぎず、コンテキストが長くなるほど
  信頼性が下がるため、実行可能なコマンド集合を静的に決める方式を採用。
- CODEOWNERS は全体には掛けず、権限境界のみに適用する
  （CI ワークフロー / asmdef / `[CliCommand]` 登録箇所 / ProjectSettings）。
  6人規模で全体に掛けると全部が同一レビュアーになり形骸化するため。
  これによりエージェント自身が権限を自己拡張する PR を通せなくなる。
- 自動テストシステムを仕様の正典とする。検証可能な振る舞いはドキュメントではなく
  テストコードで表現し、ドキュメントは機械が表現できない意図のみを担う。
- `.cs` の BOM 欠落を CI で弾く。BOM-less UTF-8 を VS2022 が CP932 と誤認識して
  文字化けするため。AGENTS.md への記載は補助的位置づけ（確率的にしか守られない）。
- AGENTS.md に記載した実行コマンドを CI で実際に実行する。
  コマンドが古くなった瞬間に CI が落ちるため、ドキュメントの腐敗が自動検出できる。
- CI 品質ゲートで asmdef の参照違反を検出する。
- JOURNAL.md の最新エントリが14日以上古い場合に警告を出す CI を入れる。
  ドキュメント習慣が死んだことの唯一の検出手段。

**ドキュメント構成**

- docs は分割しすぎず、`GDD.md` / `DECISIONS.md` / `JOURNAL.md` / `CONTRIBUTING.md` /
  `conventions.md` の5ファイルで開始する。中身が入る前に構造だけ作ると
  「整備されていない docs」という負債の見た目になるため。
  読みづらくなったら分割し、その判断もここに記録する。
- 仕様の置き場所を分離。「何を作るか」は `GDD.md`（上書き・現在の仕様のみ）、
  「なぜそうするか」は `DECISIONS.md`（追記・履歴を残す）。
  上書きされるものと追記されるものを同じファイルに入れない。
- 機能単位の受け入れ条件は GitHub Issue に書き、完了時にテストコードへ蒸留する。
  `docs/specs/` は作らない。寿命がタスク単位のものをファイルとして永続化すると腐るため。
- 数値パラメータ（敵HP・移動速度・ドロップ率等）は ScriptableObject が正典。
  ドキュメントには意図と範囲のみ書く。二重管理を避けるため。
- `conventions.md` の掲載基準は「機械で強制できず、かつ揺れると実害があるもの」のみ。
  追加前に必ず「Analyzer / .editorconfig / asmdef に落とせないか」を検討する。
  レビューで同じ指摘を2回したときだけ追加する。
- `CONTRIBUTING.md` の「1画面」制約はセットアップ節のみに緩和。
  ドキュメント運用ループは協力者も回す側であり、内部ルールではないため。

**決定記録の運用**

- ADR（Architecture Decision Record）を採用するが、標準の1判断1ファイル形式ではなく
  6人規模に合わせて `DECISIONS.md` 1枚に集約する。エージェントに章単位で渡せる利点もある。
- `DECISIONS.md`（決定・章分け・エージェントに渡す）と `JOURNAL.md`（時系列ログ・
  捕捉専用・エージェントに渡さない）を分離。理由はトークン量ではなく、ログに含まれる
  却下案や後に覆された前提をエージェントが採用済みとして誤読するリスク。
  書き込み頻度の差（週3〜5行 vs 月2〜4本）も要因。
- 記録するかの判定は1問に統一する。「これを知らない者は間違った判断をするか？」
  当初は3項目の AND 条件としていたが、却下案の有無は書式の基準であって
  記録の可否の基準ではないため誤りだった。却下案が書けない場合も記録はする。
- 量の上限は設けない。制約は「1章が単独でエージェントに渡せる長さを保つこと」。
  超えたらその章を分割する。
- `DECISIONS.md` の決定には `[D-XXX]` の連番 ID を付与する。PR やコミットメッセージから
  参照でき、章を移動しても壊れないため。欠番・再利用はしない。
- 覆された決定は削除せず `status: Superseded by D-XXX` に書き換えて残す。
  判断を更新した履歴そのものが、単発の正解より強い証拠になるため。
- 層ごとの `AGENTS.md` を「制約のみインライン、理由は D-ID 参照」の形で導入する。
  ルート AGENTS.md からのポインタは確率的遵守にすぎないため、自動ロードされる位置に
  制約を置いて機構化する。Network 層から試す。
- JOURNAL の日付は `### YYYY-MM-DD` の見出し形式とする。`<details>` による
  折りたたみも検討したが、GitHub のアウトラインに日付が出なくなるため見送り。
  週次の昇格作業をエディタ上で行う前提なら見出し折りたたみで足りる。

**環境**

- Git 環境を再構築済み（`git init` → クリーンコミット）。
  構造整理よりコミットを先に行い、revert 拠点を確保する順序を優先した。
- ラップトップを唯一の正常な作業環境として確定。
- Unity 内のファイル移動・リネームは必ず Unity Editor 上で行う。
  エクスプローラで動かすと `.meta` が追従せず GUID が壊れるため。
- PowerShell でファイルを扱う際は `[System.IO.File]::ReadAllText` で
  明示的に UTF-8 を指定する。
